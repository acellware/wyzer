---
name: Secrets Management
type: resource-linked
summary: >-
  How API keys, passwords, and certificates are stored. Frameworks expect secrets
  to be protected, not hard-coded in source code or plain configuration.
updated: 2026-09-04
cards:
  - framework: nist
    plain: >-
      Authentication secrets and cryptographic material are expected to be
      protected from disclosure and misuse.
    detail: >-
      NIST CSF 2.0 Access Control (PR.AA) and Data Security (PR.DS) cover
      protecting credentials and keys.
    citations:
      - label: "NIST CSF 2.0 · PR.AA / PR.DS"
        url: https://www.nist.gov/cyberframework
  - framework: soc2
    plain: >-
      Credentials used to access systems and data are expected to be protected
      against unauthorized access.
    detail: >-
      Maps to CC6.1 (logical access security measures over credentials and keys).
    citations:
      - label: "SOC 2 TSC · CC6.1"
        url: https://www.aicpa-cima.com/topic/audit-assurance/audit-and-assurance-greater-than-soc-2
  - framework: iso27001
    plain: >-
      Authentication information is expected to be protected, and cryptography
      used and managed appropriately.
    detail: >-
      Annex A controls A.5.17 (authentication information) and A.8.24 (use of
      cryptography) in ISO/IEC 27001:2022.
    citations:
      - label: "ISO/IEC 27001:2022 · A.5.17 / A.8.24"
        url: https://www.iso.org/standard/27001
  - framework: pci-dss
    plain: >-
      Cryptographic keys and the secrets used to protect account data are expected
      to be stored securely and access-controlled.
    detail: >-
      PCI DSS v4.0 Requirement 3.6/3.7 (key management) and Requirement 8
      (authentication) cover protecting secrets.
    citations:
      - label: "PCI DSS v4.0 · Req. 3.6 & 8"
        url: https://www.pcisecuritystandards.org/
---

**In practice.** Use a managed secrets store or vault, inject secrets at runtime,
and keep them out of source control, container images, and plain environment
files.
